## Q5. Explain the 6Rs of cloud migration.

### Senior Architect Answer

The 6Rs are common migration strategies used to decide how each application should move to cloud.

1. **Rehost** means lift and shift. We move the application to cloud with minimal changes, usually to VMs.
2. **Replatform** means making small changes to use cloud services, such as moving a web app to Azure App Service.
3. **Refactor** means changing parts of the application to improve scalability, maintainability, or cloud readiness.
4. **Rearchitect** means redesigning the application architecture, for example moving from monolith to microservices or event-driven architecture.
5. **Replace** means replacing the application with a SaaS product.
6. **Retain** means keeping the application as-is for now.
7. **Retire** means decommissioning applications that are no longer needed.

In real projects, not every application should be refactored. The right strategy depends on business value, risk, cost, timeline, and technical complexity.

### Shortcut

**Rehost = move, Replatform = small change, Refactor/Rearchitect = modernize, Replace = SaaS, Retain = keep, Retire = remove**

## Q8. Explain hub-spoke architecture.

### Senior Architect Answer

Hub-spoke architecture is a network topology where the hub VNet contains shared services and the spoke VNets host application workloads.

The hub usually contains Azure Firewall, VPN/ExpressRoute gateway, DNS, Bastion, shared monitoring, and sometimes central security services. Spoke VNets contain workloads like APIs, databases, AKS, App Services with VNet integration, or private endpoints.

The benefit is centralized security and connectivity. Traffic between on-prem and Azure or between spokes can be controlled through the hub. It also helps with governance, separation of workloads, and scalable network design.

For regulated workloads like healthcare, hub-spoke design is useful because we can centralize firewall inspection, private connectivity, logging, and control over PHI/PII data access.

### Shortcut

**Hub = shared security/connectivity. Spoke = application workloads.**

## Q9. App Service vs AKS vs Azure Functions.

### Senior Architect Answer

I choose compute based on workload type, operational complexity, scalability, and team maturity.

**Azure App Service** is suitable for standard web applications and APIs. It provides managed hosting, autoscaling, deployment slots, managed identity, VNet integration, and low operational overhead. For many enterprise APIs, App Service is the best starting point.

**AKS** is suitable when we need Kubernetes-level control, many containerized microservices, service discovery, ingress, sidecars, custom networking, advanced deployment patterns, or portability. AKS is powerful but increases operational responsibility.

**Azure Functions** is suitable for event-driven, short-running, serverless workloads such as Service Bus processing, timers, blob triggers, notifications, and background jobs.

For a healthcare claim application, I may host APIs on App Service or AKS, use Functions for event processing, and Service Bus for decoupling.

### Shortcut

**App Service = managed API hosting, AKS = Kubernetes control, Functions = event-driven processing**

## Q10. How do you design secure Azure workloads?

### Senior Architect Answer

I use defense-in-depth. Security should be applied at identity, network, application, data, and operations layers.

At identity layer, I use Entra ID, RBAC, least privilege, MFA, Privileged Identity Management, and Managed Identity. At network layer, I use VNet integration, Private Endpoints, NSGs, Azure Firewall, WAF, private DNS, and secure connectivity through VPN or ExpressRoute.

At application layer, I use APIM, JWT validation, authorization policies, input validation, secure headers, rate limiting, and proper error handling. At data layer, I use encryption at rest and in transit, Key Vault, data masking, tokenization where needed, backup, retention, and audit logging.

At operations layer, I use Defender for Cloud, Azure Monitor, Log Analytics, Application Insights, alerts, and security posture monitoring.

For healthcare workloads, PHI and PII protection is critical, so I avoid sensitive data in logs, apply strict access control, and maintain audit trails.

### Shortcut

**Identity + Network + App + Data + Monitoring + Compliance**

## Q11. Managed Identity vs Service Principal.

### Senior Architect Answer

A Service Principal is an application identity used to authenticate applications or automation scripts against Azure resources. It usually requires managing client secrets or certificates.

Managed Identity is an Azure-managed identity assigned to an Azure resource like App Service, Function App, VM, or AKS workload. With Managed Identity, Azure manages the credentials, so we do not need to store secrets in code or configuration.

For Azure-hosted workloads, I prefer Managed Identity because it reduces secret management risk. For example, an App Service can use Managed Identity to access Key Vault, Storage, Azure SQL, or Service Bus.

Service Principal is still useful for CI/CD pipelines, cross-tenant scenarios, or tools that run outside Azure.

### Shortcut

**Managed Identity = no secrets to manage. Service Principal = app identity with credential management.**

## Q12. Private Endpoint vs Service Endpoint.

### Senior Architect Answer

Both are used to secure access to Azure PaaS services, but they work differently.

A **Service Endpoint** extends the VNet identity to Azure PaaS services. Traffic still goes to the public endpoint of the service, but access is restricted to selected VNets.

A **Private Endpoint** creates a private IP address inside your VNet for the Azure service. The service becomes reachable through private IP using Azure Private Link. This is more secure and preferred for strict enterprise or regulated workloads.

For healthcare workloads involving PHI/PII, I prefer Private Endpoints for services like Storage, SQL, Key Vault, Cosmos DB, and Azure AI/Search services where supported.

### Shortcut

**Service Endpoint = secure public endpoint. Private Endpoint = private IP inside VNet.**

## Q13. How do you design high availability in Azure?

### Senior Architect Answer

High availability means designing the system to continue operating even when individual components fail.

At application level, I deploy multiple instances across availability zones where supported. For App Service, I use zone redundancy if available, autoscaling, health checks, and deployment slots. For AKS, I use multiple nodes, multiple availability zones, pod replicas, readiness/liveness probes, and autoscaling.

At data level, I use zone-redundant or geo-redundant options depending on RTO/RPO. Azure SQL can use zone redundancy, failover groups, backup, and geo-replication. Storage can use ZRS or GRS. Cosmos DB can use multi-region replication.

At network and entry layer, I use Azure Front Door, Application Gateway/WAF, Traffic Manager, or load balancers depending on architecture.

I also add monitoring, alerting, automated recovery, backup, and DR runbooks.

### Shortcut

**Multi-instance + zone redundancy + data replication + health monitoring**

## Q14. How do you design disaster recovery?

### Senior Architect Answer

Disaster recovery starts with defining RTO and RPO. RTO tells how quickly service must be restored. RPO tells how much data loss is acceptable.

Based on RTO/RPO, I select active-active, active-passive, warm standby, or backup-restore strategy.

For critical applications, I may deploy across paired Azure regions using Azure Front Door or Traffic Manager for failover. Data can be replicated using Azure SQL failover groups, Storage GRS/RA-GRS, Cosmos DB multi-region, or backup/restore depending on criticality.

I also define infrastructure as code, automated deployment, DNS failover, data recovery, security configuration replication, monitoring, and DR drills.

In healthcare, DR is important because downtime can affect patient or claim operations, so DR design must be validated regularly.

### Shortcut

**RTO/RPO → DR pattern → data replication → failover → test regularly**

## Q15. Service Bus vs Event Grid vs Event Hub.

### Senior Architect Answer

I choose based on messaging pattern.

**Service Bus** is for enterprise messaging, reliable commands, queues, topics, transactions, dead-lettering, duplicate detection, and ordered processing using sessions. I use it when message reliability is important.

**Event Grid** is for lightweight event notification. It is good when something happened and subscribers need to react, like blob created or resource changed.

**Event Hub** is for high-throughput event streaming and telemetry ingestion. It is used for logs, IoT, clickstream, or large event streams.

For claim processing, I would use Service Bus for workflow commands and reliable processing. For blob upload notification, Event Grid can trigger processing. For telemetry or high-volume data streams, Event Hub is better.

### Shortcut

**Service Bus = reliable business messaging, Event Grid = event notification, Event Hub = high-volume streaming**

## Q16. How do you ensure message reliability in Service Bus?

### Senior Architect Answer

I use Peek-Lock mode, retries, dead-letter queues, duplicate detection, idempotent consumers, MaxDeliveryCount, monitoring, and alerts.

In Peek-Lock mode, a message is locked when received but removed only after successful processing. If processing fails, the lock expires and the message can be retried. After repeated failures, the message goes to the dead-letter queue.

I also make consumers idempotent because duplicate delivery can happen. For example, before processing a claim event, I check whether the event ID or business key has already been processed.

For production, I monitor active messages, dead-letter count, processing latency, retry count, and consumer failures.

### Shortcut

**Peek-Lock + Retry + DLQ + Idempotency + Monitoring**

## Q19. What are HIPAA, PHI, and PII?

### Senior Architect Answer

HIPAA is a US healthcare regulation focused on protecting health information. PHI means Protected Health Information, which is health-related information that can identify a person. PII means Personally Identifiable Information, which is any data that can identify an individual.

Examples of PHI include diagnosis, treatment details, medical record number, claim details, lab reports, prescription data, or insurance health information. Examples of PII include name, email, phone number, address, date of birth, Aadhaar/PAN/SSN, or other identifiers.

For such data, cloud architecture must include encryption, least-privilege access, masking, audit logs, secure storage, retention policies, and strict monitoring. Sensitive data should not be logged unnecessarily.

### Shortcut

**PHI = health identifiable data. PII = personal identifiable data. HIPAA = rules to protect health data.**

## Q20. How would you design healthcare claims processing on Azure?

### Senior Architect Answer

I would design healthcare claims processing as a secure event-driven architecture.

Claims may come through portal, API, email, or batch upload. The intake API validates the request, stores documents in Blob Storage, stores metadata in Azure SQL or Cosmos DB, and publishes a `ClaimReceived` message to Service Bus.

Downstream services process eligibility validation, policy/member verification, provider validation, fraud checks, document extraction, claim adjudication support, vendor routing, and notifications. Long-running processes can be orchestrated using Durable Functions or workflow orchestration.

For security, I would use APIM, Entra ID, Managed Identity, Key Vault, Private Endpoints, encryption, RBAC, WAF, audit logs, data masking, and strict PHI/PII controls. For observability, I would use Application Insights, Log Analytics, dashboards, alerts, and correlation IDs.

AI can help with document extraction, claim summarization, duplicate claim detection, and knowledge search, but critical decisions should have governance and human review.

### Architecture

```text
Portal / Email / API / Batch
        ↓
APIM / WAF
        ↓
Claim Intake API
        ↓
Blob Storage + Claim DB
        ↓
Service Bus
        ↓
Validation Services
        ↓
Fraud / Rules / AI Assistance
        ↓
Vendor Routing / Manual Review
        ↓
Notification + Audit
```

## Scenario 1. A client has 100 legacy applications. How will you create a cloud migration roadmap?

### Senior Architect Answer

I would not migrate all 100 applications randomly. I would first create an application portfolio assessment. For each application, I would capture business criticality, technology stack, dependencies, database, integrations, security requirements, performance needs, user base, deployment complexity, and support status.

Then I would classify applications using the 6Rs: rehost, replatform, refactor, rearchitect, replace, retain, or retire. I would also identify quick wins, high-risk applications, and applications that should move together because of dependencies.

Next, I would define the target architecture, landing zone, network, identity, security baseline, migration waves, data migration approach, testing plan, cutover strategy, and rollback plan.

The roadmap would be phased: first foundation, then low-risk migration, then modernization of high-value applications, and finally optimization.

## Scenario 2. A healthcare client wants to move claims application to cloud. What will you do?

### Senior Architect Answer

I would start with discovery: current architecture, claim intake channels, databases, integrations, compliance requirements, PHI/PII data flow, reporting needs, SLAs, RTO/RPO, and dependencies.

Then I would define a secure Azure target architecture using APIM, App Service/AKS, Service Bus, Azure SQL/Cosmos DB, Blob Storage, Key Vault, Managed Identity, Private Endpoints, WAF, Application Insights, and Log Analytics.

Claims processing should be event-driven because it involves multiple steps like validation, document processing, fraud check, vendor routing, and notification. For long-running flows, I would use Durable Functions or orchestration.

Because it is healthcare, I would prioritize encryption, audit logging, data masking, access control, PHI/PII protection, retention, monitoring, and compliance.

## Scenario 3. A client asks to reduce cloud cost by 30%. How will you approach?

### Senior Architect Answer

I would approach cost optimization using a FinOps mindset. First, I would analyze current spend by subscription, resource group, application, environment, and service. I would check whether resources are tagged correctly.

Then I would identify unused or underutilized resources, over-provisioned compute, idle disks, expensive SKUs, oversized databases, unnecessary public IPs, and non-production resources running 24x7.

Optimization actions may include right-sizing, autoscaling, reserved instances or savings plans, storage lifecycle policies, database tuning, caching, shutting down dev/test environments after hours, and moving suitable workloads to serverless or PaaS.

I would also set budgets, alerts, cost dashboards, and governance policies so cost remains controlled.

---

## Scenario 4. Client has public APIs but private backend services. How will you design connectivity?

### Senior Architect Answer

I would expose public APIs through APIM or Application Gateway/WAF, but backend services should remain private. If APIM is public and backend is private, APIM must have private network connectivity to the backend, such as APIM in external VNet mode or internal APIM behind Application Gateway.

Backend services can be hosted in App Service with Private Endpoint, AKS internal services, or internal load balancer. Private DNS must be configured correctly. Backend should allow traffic only from APIM or the gateway path. I would also use JWT validation, managed identity, mTLS if required, NSGs, firewall rules, and monitoring.

---

## Scenario 5. Client wants AI-enabled document Q&A over healthcare policies. How will you design it?

### Senior Architect Answer

I would design a secure RAG-based architecture. Policy documents are stored in Blob Storage or SharePoint. An ingestion pipeline extracts text, chunks documents, generates embeddings using Azure OpenAI, and stores chunks with metadata in Azure AI Search.

At runtime, users ask questions through a secured web/API layer. The API authenticates the user, applies authorization and security trimming, retrieves only allowed document chunks from Azure AI Search, and sends the grounded context to Azure OpenAI. The model returns answers with citations.

For healthcare, I would ensure PHI/PII protection, audit logs, private endpoints, content filtering, prompt injection checks, and no unnecessary sensitive prompt logging. I would also evaluate answer quality using a golden dataset and capture user feedback.
